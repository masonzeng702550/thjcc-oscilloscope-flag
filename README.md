# Oscilloscope-music CTF challenge — `THJCC{δράκος}`

Flag 以「示波器音樂」（X-Y / Lissajous）方式編碼：左聲道 = X、右聲道 = Y，
把兩個聲道當散點圖畫出來就是文字。再疊兩層刻意的破壞，讓最直覺的畫法看不出東西。

## 檔案

| 檔案 | 用途 |
|---|---|
| `challenge.wav` | **給選手的題目檔**（48kHz / 16-bit stereo / 10s，無損首選） |
| `challenge.flac` | 同上，無損壓縮版 |
| `challenge.mp3` | 320k 版本，實測可解（見下方 MP3 說明） |
| `reference_clean.wav` | 未破壞的參考檔（**出題者留存，不要發布**） |
| `generate.py` | 產生器 |
| `solve.py` | 官方解 |
| `step1_naive_xy.png` | 選手直接畫 X-Y 會看到的東西 |
| `step2_solved_xy.png` | 正確解出的結果 |

## 編碼與破壞

1. **X-Y 向量繪圖** — 字形輪廓（DejaVu Sans Bold，含希臘字母與 tonos）
   取出後依弧長等距重取樣，每 3000 samples 走完一整圈（約 16 fps refresh）。
2. **破壞層 1 — Mid/Side**：`ch0 = (L+R)/2`、`ch1 = (L-R)/2`。
   這會讓圖整個旋轉 45°。
3. **破壞層 2 — 聲道延遲**：`ch1` 往後推 **1129 samples**。
   這是主要難點，會讓 X 和 Y 取自路徑上不相干的兩點，圖徹底糊掉。

解題必須**反序**還原：先對齊延遲，再解 M/S。

## 官方解法

```bash
python3 solve.py challenge.wav
```

自動搜尋延遲的判準是 **最小化光跡總路徑長度**。對齊正確時軌跡沿著平滑的字形
輪廓走，路徑最短；對齊錯誤時 X、Y 互相亂配，軌跡劇烈抖動、長度暴增。

實測：1.9 秒內精準還原 delay = 1129。

> 注意：一開始我用「佔用格子數最少」當判準，會誤鎖到 1162，畫出看似有字但扭曲
> 的圖 — 這類**接近但錯誤**的局部最佳解正是本題卡人的地方，可以預期選手會踩到。

## 能不能把 flag 藏進「一首歌」裡？（已實測，`test_music_carrier.py`）

**不能。** 這是數學限制，不是工具限制 — 示波器繪圖**就是**波形本身，那些取樣值
同時定義了圖形。音樂疊上去，X-Y 圖顯示的就是音樂的立體聲場，不是文字。

實測用合成的密集流行樂底（113 BPM、四四拍、失諧鋸齒 pad、寬立體聲、軟限幅）：

### Test A — 拼接（音樂 → payload → 音樂）✅ 可行

delay 精準還原 1129，文字完全可讀。這是唯一實際可行的做法。
代價：payload 段是刺耳嗡鳴，任何人一聽就知道那段有問題。

### Test B — 混音（payload 疊在音樂上）❌ 不可行

| 音樂音量 | 佔用率 | 結果 |
|---|---|---|
| 0.00（無） | 0.042 | 基準 |
| 0.05 | 0.197 | 已劣化（4.7x 模糊） |
| 0.10 | 0.245 | 已劣化（5.8x） |
| 0.20 | 0.279 | **不可讀**（6.6x） |
| 0.35 | 0.310 | 不可讀（7.4x） |
| 0.60 | 0.310 | 不可讀（7.4x） |

關鍵數字：0.05 已經是 **−26 dB**，也就是幾乎聽不見的音量，文字就已經開始糊掉。
「音樂大聲到能聽出是哪首歌」和「文字還讀得出來」這兩件事沒有交集。

結論：想要有音樂感，只能用 **Test A 的拼接**，不要期待混音式的隱藏。

## 有音樂版本（`make_musical_challenge.py`）

`musical_challenge.wav` / `.mp3` — 53 秒，完整編曲結構：

```
intro (4 bars) -> main (8) -> build (4) -> [PAYLOAD 6s] -> outro (6, fade)
                                            34.16s ~ 40.16s
```

payload 是**拼接**進去的（不是混音），前後各留 0.18s 空白當作接縫。
整檔一樣套 Mid/Side + delay 1129。

實測：WAV 與 MP3 320k 都能精準還原 delay=1129，文字完全乾淨。

### solver 的 payload 定位（重要）

音樂版把「用音量找 payload」這招打死了 — 母帶處理過的音樂比 payload 還大聲。
最終判準是**同時要求「夠大聲」且「長 lag 高度週期」**：

- 只看音量 → 被大聲的音樂騙（音樂版失敗）
- 只看週期性 → 被持續的 pad 音騙，純音真的是完美週期（簡單版失敗）
- 兩者同時 → 三個檔案全部精準切出 5.97s

實作有個坑：自相關必須用**無偏正規化**（除以重疊長度 `block - lag`，
而非除以 `block`）。否則長 lag 純粹因為重疊少而被懲罰，payload 只拿到 0.63 分，
反而輸給音高週期的 pad（0.89）。修正後 payload 是 0.995。

驗證結果：

| 檔案 | 切出長度 | delay |
|---|---|---|
| `challenge.wav` | 5.97s / 10.00s | 1129 ✅ |
| `musical_challenge.wav` | 5.97s / 53.09s | 1129 ✅ |
| `musical_challenge.mp3` (320k) | 5.97s | 1129 ✅ |
| `test_splice.wav` | 5.97s / 14.00s | 1129 ✅ |

## 主辦方範例歌曲版本（`make_song_challenge.py`）

用 `~/Downloads/all_nigh_long.mp3`（9.53s / 44.1kHz / 320k / 無 metadata tag）當底。
全程走原生 44.1kHz，不重採樣來源；frame rate 因此變成 44100/3000 = **14.7 fps**。

payload 拼在 **4.93s ~ 10.92s**，總長 15.88s。
WAV 與 MP3 320k 都精準還原 delay=1129，文字乾淨。

### ⚠️ 這首歌是單聲道 — 會洩漏 payload 位置

| 量測 | 數值 | 意義 |
|---|---|---|
| L/R 相關係數 | **0.9998** | 幾乎完全單聲道 |
| side/mid 能量比 | 0.0098 | 側訊號只有 1% |
| side RMS：歌 vs payload | 0.00243 vs 0.27548 | **114 倍落差** |

後果：套上 Mid/Side 之後，ch1（side）在歌曲段幾乎是**一條直線**，payload 段
卻是滿幅方塊。選手用任何波形檢視器一開就看到 payload 在哪 —
見 `song_side_giveaway.png`。

註：payload 的 side 能量無法降低 — 側訊號**就是**圖形本身。
所以修正只能從來源那一側下手。

### 修正：立體聲去相關（`widen_song.py`，已套用）

用 **Mid/Side + 全通濾波器串接** 加寬來源：

```
S_new = allpass_cascade(M) * width
L = M + S_new,  R = M - S_new
```

選全通濾波器（Schroeder，延遲 137/229/349/521，g=0.7）而非 Haas delay 的理由：

- 全通只改**相位**、不改振幅 → 歌曲音色與頻譜完全不變，只是不再是單聲道
- 單聲道總和 `L+R` 精確塌回 `2M` → 完美 mono 相容，不會產生可聽見的假影

寬度掃描結果：

| width | L/R corr | side RMS | 對比 |
|---|---|---|---|
| 原始 | 0.9998 | 0.00243 | 114x |
| 0.10 | 0.9809 | 0.02319 | 11.9x |
| **0.30** | **0.8396** | **0.05930** | **4.6x** ← 採用 |
| 0.45 | 0.6703 | 0.07961 | 3.5x |
| 0.80 | 0.2235 | 0.10879 | 2.5x |

採用 **0.30**：對比從 114x 降到 5x（改善 25 倍），而 L/R 相關 0.84 仍是
一般商業混音的正常寬度，不會聽起來怪。

對照 `song_side_giveaway.png`（修正前）與 `song_side_widened.png`（修正後）：
side 通道從「歌曲段一條直線」變成全程都有內容，payload 不再獨自站在空白上。

修正後 WAV 與 MP3 320k 仍精準還原 delay=1129。

## 音樂會變嗎?（`check_audible_change.py`，已實測）

分兩層，結論不同。

### 加寬那層：完全沒變

| 指標 | 結果 |
|---|---|
| 單聲道總和 `L+R` 差異 | **−227.9 dB**（浮點數的零） |
| 各頻段振幅差異（20Hz–20kHz，8 段） | 全部 **0.00 dB** |

驗證了全通濾波器的理論保證：只改相位、不改振幅。音色與 EQ 平衡完全沒動。

### 破壞層：數字上變很多，但聽不出來

M/S + delay 是套用在**整個檔案**上，包含歌曲段：

| 指標 | 原始 | 題目檔播放時 |
|---|---|---|
| 左聲道 vs 原始 | — | corr +0.9999 |
| 右聲道 vs 原始 | — | corr −0.0352 |
| L/R 相關 | +0.9998 | −0.0352 |
| 左右音量差 | ~0 dB | 10.6 dB |

**但實聽確認：聽不出來。** 原因是這首歌接近單聲道，所以 Mid ≈ 完整的歌
（左聲道幾乎原封不動），而 Side 只有 −22 dB 很容易忽略；任何往單聲道混的
播放方式又會把 `L+R` 加回接近原曲。

因此**維持現狀**：破壞套用於整個檔案，不需要只針對 payload 段。
（若日後換成立體聲較寬的來源，這個結論要重新驗證 —— 那時 Side 不再是小訊號。）

## 红队實測結果（隔離 agent，未解出）

給一個 agent 只有 `song_challenge.wav`（改名為 `audio_challenge.wav`、去除檔名線索），
禁止搜尋檔案系統其他位置、禁止上網。結果：

| 項目 | 數值 |
|---|---|
| 執行時間 | **88 分鐘** |
| 工具呼叫 | 146 次 |
| Token 用量 | 306,609 |
| 嘗試的假設 | 22 個 |
| 自評死路比例 | **85–90%** |
| 結果 | **未解出** |

### 關鍵發現：它找到了兩層破壞，然後把兩層都否決了

這是本題設計最有效的部分，值得記錄：

- **第 6 步**：試了 Mid/Side（45°）旋轉 —— 「排版變成大致水平的兩列，
  但字形仍然不可讀且重疊」→ **判定此路不通**
- **第 11 步**：掃描聲道延遲（±1500）與互相關 —— **「最佳 lag = −1130，r=0.60」**
  → **判定「不是延遲嵌入」**

真實延遲是 **1129**。它在第 11 步就把答案算出來了，然後丟掉。

原因：**兩層破壞必須同時、依正確順序還原**。單獨解 M/S → 仍是垃圾；
單獨對齊 delay → 仍是垃圾。每一層單獨測試都會得到否定的結果，
於是正確的假設被逐一排除。

這正是疊加兩層的價值 —— 不是讓每一層更難，而是讓**正確答案在單獨驗證時看起來是錯的**。

### 次要發現：重複字元偵測產生了誤導

第 18 步它做了很聰明的檢查：`THJCC{...}` 裡有相鄰的 `CC`，如果真是字型渲染的文字，
應該找得到近乎 1.0 的重複片段。實測只有 **0.61**，於是它推翻了「這是文字」的核心假設。

推理正確，但前提有瑕疵：在**未修復**的視圖裡，兩個 C 位於路徑上不同位置，
在錯誤的延遲下會映射成不同的扭曲形狀。這個假陰性把它推向完全錯誤的方向。

### 它自己的結論

最後它認為 flag 可能是**用講的**藏在音樂段裡，並指出「我沒有音訊播放能力，
這是我唯一無法檢查的通道」。這是死路，但揭露了 agent 的真實感知缺口。

### 第二次红队：給提示後解出（15.9 分鐘）

同一個檔案，同樣的隔離條件，但起始指令附上 HINT 1 + HINT 2（**故意不給**第三層的順序提示）。

| | 第一次（無提示） | 第二次（HINT 1+2） |
|---|---|---|
| 結果 | **未解出** | **解出 `THJCC{δράκος}`** |
| 時間 | 88 分鐘 | **15.9 分鐘** |
| 工具呼叫 | 146 | 40 |
| Token | 306,609 | 135,206 |
| 自評死路比例 | 85–90% | 40% |

結論：**提示 1+2 就足夠，第三層（順序）不需要。**

### 重要：HINT 1 是有害的，必須改寫

第二個 agent 的原話：

> 「『拿來看的、不是看波形』最自然的讀法就是**頻譜圖**，我第一步就去畫了 —— 死路。
> ⋯⋯這個提示指向大致正確的方向，但它最顯而易見的解讀是個誘餌。」

以及：

> 「HINT 1 大概反而**拉長**了我的時間，因為它把我先送去頻譜圖。」

原版 HINT 1 把人推向這題**唯一保證無效**的視角。建議改成明確排除法：

> **修正版 HINT 1**：「不是看波形，也不是看頻譜圖。」

這樣既砍掉最大的死路，又不洩漏 X-Y。

### HINT 2 是承重的那一個

它明確指出 HINT 2 改變了做法：

> 「HINT 2 告訴我有**兩件**事要還原：一個線性混合**加上**一個延遲。
> 這讓我去明確尋找延遲，而且關鍵是 —— 讓我把那兩個孿生暫態事件解讀成
> **同一組事件的兩種對齊**，而不是兩個獨立的來源。
> 沒有這個框架，我大概會一直在未位移的 L/R 上試 2×2 解混，那是不可能成功的。」

這與第一次失敗的原因完全吻合。

### 技術發現：延遲對 3000 取模是模糊的

第二個 agent 找到的延遲是 **1871**，不是 1129 —— 它自己注意到 **1129 + 1871 = 3000**。

因為 payload 是週期 3000 的完美循環，延遲只在**模 3000 意義下**有定義。
`solve.py` 鎖定 1129，agent 用 1871，兩者等價。這代表**存在兩條等價的解題路徑**，
不是 bug，但出題時要知道：選手報告的延遲值可能是 1871。

### 意外的設計收穫：雙行排版

它說真正最難的一步不是提示涵蓋的任何一項：

> 「真正困難的部分 —— 意識到這是**兩行**文字，這才是修正解混的關鍵 ——
> 來自看我自己畫的圖，不是來自任何一個提示。」

雙行排版讓 X 軸變成**雙齒鋸齒波**，這個結構是最終正確解混的依據。
當初分兩行只是為了讓字填滿 X-Y 方框，意外成為難度的主要來源。

### 一個要保留懷疑的自評

它宣稱沒有提示也能解出，只是慢 1.5–2 倍。**但這與唯一的無提示數據點矛盾**——
第一個 agent 沒有提示，跑了 88 分鐘失敗。

兩邊各只有 n=1，而且第二個 agent 用了第一個從未嘗試的技術（畫格平均、暫態事件取證）。
所以差異可能來自運氣或技術選擇，不完全來自提示。**不要把「1.5–2 倍」當成可靠估計。**

### 誘餌段落驗證有效

它檢查了其餘三段音樂區域，確認無週期性、無 X-Y 結構，是純粹的誘餌。設計如預期運作。

### 對難度的判讀

**這題目前可能過難。** 一個有充分工具的 agent 花 88 分鐘、22 個假設仍毫無進展，
人類選手在比賽時限內解出的機率很低。建議搭配分段提示 —— 見下節。


## ⚠️ 意外的巧合：1871 有雙重身分（重要，影響參數鎖定）

畫格裡 18 個輪廓的起始位置經計算為：

```
6, 215, 426, 496, 680, 749, 806, 974, 1038, 1253,
1323, 1463, 1662, 1871, 2077, 2365, 2540, 2773
```

第 14 個輪廓 —— 也就是 **`THJCC` 這一行的第一筆** —— 起始於取樣 **1871**。

而 **3000 − 1129 = 1871**，也就是延遲的補數（等價的位移量）。

這兩件事在成因上完全無關，卻撞在同一個數字上：

| 1871 的身分 | 成立嗎 |
|---|---|
| 第二行文字的起始位置 | ✅ 真的，是排版的實際結構 |
| 延遲的等價位移量 | ✅ 也是真的，用它做時間位移即可解開 |

### 為什麼這讓題目大幅變難

五個無提示 agent 中有兩個（rt_a、rt_b2）找到了 1871，並判讀為
「兩行文字的分界」—— **判讀正確**。於是他們把畫格切成 `row1` / `row2` 分開處理。

**正因為這個解釋是對的，他們沒有理由再去試「把它當成時間位移」。**
rt_a 的延遲相關腳本數是 **0** —— 它完全不認為有延遲問題存在。

對照解出的那個 agent：它同樣找到 1871，但來源是**互相關的次要峰值**，
所以從一開始就把它當成位移量。同一個數字，不同的發現路徑，決定了成敗。

正確答案被藏在另一個**同樣正確、但不同層次**的答案背後。

### 這是運氣，不是設計 —— 參數要鎖定

`DELAY = 1129` 是隨手挑的，輪廓落點由字型週長與四捨五入決定。這個碰撞純屬意外。

- 換 flag 內容、換排版、或改 `DELAY` → **碰撞消失，題目明顯變簡單**
- 想保留這個難度 → **鎖定現行參數**（`DELAY=1129` + 雙行 `THJCC` / `{δράκος}`）
- 覺得太兇殘 → 把 `DELAY` 改成例如 1400 即可破除

任何參數變動後都必須重跑红队，不能假設難度不變。

## 難度評估（對 AI agent）

主要門檻在**視角**，不在計算：

- agent 的標準流程是「畫波形 → 畫頻譜 → 看 metadata → binwalk」，
  這四步在本題全部無效。
- 「把立體聲當 X-Y 散點圖畫」不在預設清單裡，這是最大的一道關。
- 但一旦想到了，後面的 cross-correlation / 參數搜尋 agent 反而比人類快。

預期效果原估「從 5 分鐘拉到 40–90 分鐘」。實測 88 分鐘**仍未解出**，
比預期更硬 —— 主因是兩層破壞的交互作用（見上節），而非單層難度。

### 建議的分段提示

如果要讓題目可解，建議提供遞進式提示：

1. **「不是看波形，也不是看頻譜圖。」**
   （實測必須用**排除法**寫。原本寫成「拿來看的但不是波形」會被讀成「去畫頻譜圖」，
   那是本題唯一保證無效的視角，反而拉長解題時間。）
2. **「兩個聲道被混在一起了，而且其中一個遲到了。」**
   （點出有**兩個**問題，這是關鍵 —— 防止選手單獨測試後放棄）
3. **「先對齊時間，再解開混合。順序不能反。」**

第 2 個提示最重要。红队失敗的直接原因就是不知道要**同時**處理兩層。

## 五個並行 agent 的批次測試（中斷，不可作為解出率）

在無提示條件下同時派出五個隔離 agent。**這批實驗未完成** —— 五個都在跑了
90+ 分鐘後被外部 process 結束砍斷，且事後無法恢復（transcript 未落地）。

**因此「0/5 解出」不成立**，它們是被中斷、不是自己放棄。這是實驗事故，不是實驗結果。

不過被砍斷前的檔案殘骸仍支持既有結論：

| Run | 檔案 | 腳本 | 延遲相關腳本 | 找到 1871 |
|---|---|---|---|---|
| A | 97 | 38 | **0** | 5 次（當行分界用） |
| B | 90 | 33 | 2 | 1 次（當行分界用） |
| C | 110 | 38 | 1 | ❌ |
| D | 69 | 32 | 1 | ❌ |
| E | 113 | 43 | 1 | ❌ |

- 五個全部超過第一個 agent 投降的 88 分鐘，**沒有一個接近成功**
- 合計 184 個腳本，**只有 5 個碰過延遲估計**
- 找到 1871 的兩個，**都判讀為行分界，零個當成時間位移**

最後的寫入檔名（`band_C.png`、`mirror_B.png`、`four_-48.9.png`、`seg_s3R.png`）
顯示五個在被砍斷時仍在掃旋轉／鏡射／分頻帶參數 —— 與第一個 agent 相同的死路。

## 結論與出題建議（最終）

證據總表：

| 條件 | 樣本 | 結果 |
|---|---|---|
| 無提示 | n=1 完整 | 88 分鐘**失敗** |
| 無提示 | n=5 中斷 | 90+ 分鐘**全部無進展** |
| 有提示（HINT 1+2） | n=1 完整 | **16 分鐘解出** |

**出題決策：**

1. **必須附提示。** 不附，大概率零解。
2. **HINT 1 用排除法版本**：「不是看波形，也不是看頻譜圖。」
   原版（「拿來看的但不是波形」）會把人送去頻譜圖，那是原理上唯一無效的視角。
3. **HINT 2 是承重的**：「兩個聲道被混在一起了，而且其中一個遲到了。」
   關鍵在於讓選手知道有**兩個**故障，必須一起修 —— 這正是所有失敗案例的共同死因。
4. **第三層（順序）不需要**，實測有 1+2 就夠。
5. **鎖定現行參數。** 難度部分建立在 1871 的巧合上（見上節），
   改 flag、改排版、改 DELAY 都會顯著降低難度，且必須重跑红队驗證。

預期難度：附提示後，強隊約 15–30 分鐘。適合當中高分題。

## 敘述措辭的完整實測（四種版本）

把提示寫進**題目敘述**（不扣分、每隊起跑點一致）而非當成付費 hint，測了四種措辭：

| 敘述 | 時間 | 結果 |
|---|---|---|
| 無敘述 | 88 分鐘 | ❌ 失敗 |
| 「拿來看的，但不是波形」+ 具體版 | **15.9 分鐘** | ✅ **最快** |
| 「壞了兩次」+ 頻譜圖句（兩句都抽象） | 停擺 | ❌ 失敗，109 檔案**從未畫過 X-Y** |
| 頻譜圖句 + 具體版 | 44.4 分鐘 | ✅ 解出 |

### 反直覺的結論：我「改良」的頻譜圖句其實更差

原本推論「明確排除頻譜圖」會比「不是波形」更好。實測相反 —— 15.9 分鐘 vs 44.4 分鐘。

原因在最後一次的自述：

> 「『頻譜圖丟掉的東西』最標準的讀法就是**相位**，所以我花了一整步去做 STFT 相位圖
> 和聲道間相位差圖，想找一張畫在相位裡的圖。那是繞路。
> 真正的讀法更廣：頻譜圖丟掉的是**波形本身** —— 兩個聲道逐取樣的聯合軌跡。」

也就是說**兩個版本都會造成繞路**，只是繞法不同：

- 「不是波形」→ 被讀成「那就頻譜圖」→ 繞一小圈
- 「頻譜圖丟掉的」→ 被讀成「相位」→ 繞進 STFT 相位的死胡同（更深）

「相位」這個陷阱在兩次獨立測試中都出現，是穩定的失敗模式。

### 具體版那句也有歧義，且代價高昂

> 「**One of them is late**」中的 them 是指兩個**來源訊號**，還是兩個**混合後的聲道**？
> 我讀成『一個來源』，於是一直在分離出來的第二個分量上套補償性的循環位移 ——
> 大約兩小時的掃描全浪費在這。正確讀法是混合發生在延遲**之後**。」

這佔了它 45–50% 的總工時。**最小修正:把 `one of them` 改成 `one channel`**，
消除「來源 vs 聲道」的歧義。

### 建議的最終敘述

```
DOUBLE FAULT                                    [ audio ]

Meant to be looked at, not listened to -- and not as a waveform.
The two channels have been mixed together, and one channel is late.
```

- 第一句用**實測最快的版本**（15.9 分鐘那個），不用「頻譜圖丟掉的東西」——避開相位陷阱
- 第二句把 `one of them` 改為 `one channel`——消除歧義（此修正未實測，但針對已診斷的具體病灶）

### 第二次有人宣稱「沒敘述也能解」

這次的 agent 同樣說沒有敘述也能解、甚至更快，理由是**第 7 步的原始 X-Y 散點圖在任何解混之前
就已經顯示出可辨識的字母**。

但無敘述條件的直接證據是：n=1 完整失敗（88 分鐘）+ n=5 中斷（90 分鐘無進展、零個畫 X-Y）。
兩個解出者都事後覺得「這很簡單」，這是典型的後見之明偏誤。**不採信。**

### 一句值得記下的方法學觀察

> 「我寫的那些評分啟發式，一律比『畫成網格然後用眼睛看』更差。
> 每一次真正的突破都來自我檢視的一張圖，不是來自最佳化器。」

這同時解釋了為什麼本題對 agent 特別難：它獎勵視覺判斷，懲罰參數搜尋。
