# Oscilloscope-music CTF challenge — `THJCC{δράκος}`

Flag 以「示波器音樂」（X-Y / Lissajous）方式編碼：左聲道 = X、右聲道 = Y，
把兩個聲道當散點圖畫出來就是文字。再疊兩層刻意的破壞，讓最直覺的畫法看不出東西。

## 檔案

| 檔案 | 用途 |
|---|---|
| `challenge.wav` | **給選手的題目檔**（48kHz / 16-bit stereo / 10s，無損首選） |
| `challenge.flac` | 同上，無損壓縮版 |
| `challenge.mp3` | 320k 版本，實測可解（見下方 MP3 說明） |
| `reference_clean.wav` | 未破壞的參考檔（**出題者留存，不要發布**） |
| `generate.py` | 產生器 |
| `solve.py` | 官方解 |
| `step1_naive_xy.png` | 選手直接畫 X-Y 會看到的東西 |
| `step2_solved_xy.png` | 正確解出的結果 |

## 編碼與破壞

1. **X-Y 向量繪圖** — 字形輪廓（DejaVu Sans Bold，含希臘字母與 tonos）
   取出後依弧長等距重取樣，每 3000 samples 走完一整圈（約 16 fps refresh）。
2. **破壞層 1 — Mid/Side**：`ch0 = (L+R)/2`、`ch1 = (L-R)/2`。
   這會讓圖整個旋轉 45°。
3. **破壞層 2 — 聲道延遲**：`ch1` 往後推 **1129 samples**。
   這是主要難點，會讓 X 和 Y 取自路徑上不相干的兩點，圖徹底糊掉。

解題必須**反序**還原：先對齊延遲，再解 M/S。

## 官方解法

```bash
python3 solve.py challenge.wav
```

自動搜尋延遲的判準是 **最小化光跡總路徑長度**。對齊正確時軌跡沿著平滑的字形
輪廓走，路徑最短；對齊錯誤時 X、Y 互相亂配，軌跡劇烈抖動、長度暴增。

實測：1.9 秒內精準還原 delay = 1129。

> 注意：一開始我用「佔用格子數最少」當判準，會誤鎖到 1162，畫出看似有字但扭曲
> 的圖 — 這類**接近但錯誤**的局部最佳解正是本題卡人的地方，可以預期選手會踩到。

## 能不能把 flag 藏進「一首歌」裡？（已實測，`test_music_carrier.py`）

**不能。** 這是數學限制，不是工具限制 — 示波器繪圖**就是**波形本身，那些取樣值
同時定義了圖形。音樂疊上去，X-Y 圖顯示的就是音樂的立體聲場，不是文字。

實測用合成的密集流行樂底（113 BPM、四四拍、失諧鋸齒 pad、寬立體聲、軟限幅）：

### Test A — 拼接（音樂 → payload → 音樂）✅ 可行

delay 精準還原 1129，文字完全可讀。這是唯一實際可行的做法。
代價：payload 段是刺耳嗡鳴，任何人一聽就知道那段有問題。

### Test B — 混音（payload 疊在音樂上）❌ 不可行

| 音樂音量 | 佔用率 | 結果 |
|---|---|---|
| 0.00（無） | 0.042 | 基準 |
| 0.05 | 0.197 | 已劣化（4.7x 模糊） |
| 0.10 | 0.245 | 已劣化（5.8x） |
| 0.20 | 0.279 | **不可讀**（6.6x） |
| 0.35 | 0.310 | 不可讀（7.4x） |
| 0.60 | 0.310 | 不可讀（7.4x） |

關鍵數字：0.05 已經是 **−26 dB**，也就是幾乎聽不見的音量，文字就已經開始糊掉。
「音樂大聲到能聽出是哪首歌」和「文字還讀得出來」這兩件事沒有交集。

結論：想要有音樂感，只能用 **Test A 的拼接**，不要期待混音式的隱藏。

## 有音樂版本（`make_musical_challenge.py`）

`musical_challenge.wav` / `.mp3` — 53 秒，完整編曲結構：

```
intro (4 bars) -> main (8) -> build (4) -> [PAYLOAD 6s] -> outro (6, fade)
                                            34.16s ~ 40.16s
```

payload 是**拼接**進去的（不是混音），前後各留 0.18s 空白當作接縫。
整檔一樣套 Mid/Side + delay 1129。

實測：WAV 與 MP3 320k 都能精準還原 delay=1129，文字完全乾淨。

### solver 的 payload 定位（重要）

音樂版把「用音量找 payload」這招打死了 — 母帶處理過的音樂比 payload 還大聲。
最終判準是**同時要求「夠大聲」且「長 lag 高度週期」**：

- 只看音量 → 被大聲的音樂騙（音樂版失敗）
- 只看週期性 → 被持續的 pad 音騙，純音真的是完美週期（簡單版失敗）
- 兩者同時 → 三個檔案全部精準切出 5.97s

實作有個坑：自相關必須用**無偏正規化**（除以重疊長度 `block - lag`，
而非除以 `block`）。否則長 lag 純粹因為重疊少而被懲罰，payload 只拿到 0.63 分，
反而輸給音高週期的 pad（0.89）。修正後 payload 是 0.995。

驗證結果：

| 檔案 | 切出長度 | delay |
|---|---|---|
| `challenge.wav` | 5.97s / 10.00s | 1129 ✅ |
| `musical_challenge.wav` | 5.97s / 53.09s | 1129 ✅ |
| `musical_challenge.mp3` (320k) | 5.97s | 1129 ✅ |
| `test_splice.wav` | 5.97s / 14.00s | 1129 ✅ |

## 主辦方範例歌曲版本（`make_song_challenge.py`）

用 `~/Downloads/all_nigh_long.mp3`（9.53s / 44.1kHz / 320k / 無 metadata tag）當底。
全程走原生 44.1kHz，不重採樣來源；frame rate 因此變成 44100/3000 = **14.7 fps**。

payload 拼在 **4.93s ~ 10.92s**，總長 15.88s。
WAV 與 MP3 320k 都精準還原 delay=1129，文字乾淨。

### ⚠️ 這首歌是單聲道 — 會洩漏 payload 位置

| 量測 | 數值 | 意義 |
|---|---|---|
| L/R 相關係數 | **0.9998** | 幾乎完全單聲道 |
| side/mid 能量比 | 0.0098 | 側訊號只有 1% |
| side RMS：歌 vs payload | 0.00243 vs 0.27548 | **114 倍落差** |

後果：套上 Mid/Side 之後，ch1（side）在歌曲段幾乎是**一條直線**，payload 段
卻是滿幅方塊。選手用任何波形檢視器一開就看到 payload 在哪 —
見 `song_side_giveaway.png`。

註：payload 的 side 能量無法降低 — 側訊號**就是**圖形本身。
所以修正只能從來源那一側下手。

### 修正：立體聲去相關（`widen_song.py`，已套用）

用 **Mid/Side + 全通濾波器串接** 加寬來源：

```
S_new = allpass_cascade(M) * width
L = M + S_new,  R = M - S_new
```

選全通濾波器（Schroeder，延遲 137/229/349/521，g=0.7）而非 Haas delay 的理由：

- 全通只改**相位**、不改振幅 → 歌曲音色與頻譜完全不變，只是不再是單聲道
- 單聲道總和 `L+R` 精確塌回 `2M` → 完美 mono 相容，不會產生可聽見的假影

寬度掃描結果：

| width | L/R corr | side RMS | 對比 |
|---|---|---|---|
| 原始 | 0.9998 | 0.00243 | 114x |
| 0.10 | 0.9809 | 0.02319 | 11.9x |
| **0.30** | **0.8396** | **0.05930** | **4.6x** ← 採用 |
| 0.45 | 0.6703 | 0.07961 | 3.5x |
| 0.80 | 0.2235 | 0.10879 | 2.5x |

採用 **0.30**：對比從 114x 降到 5x（改善 25 倍），而 L/R 相關 0.84 仍是
一般商業混音的正常寬度，不會聽起來怪。

對照 `song_side_giveaway.png`（修正前）與 `song_side_widened.png`（修正後）：
side 通道從「歌曲段一條直線」變成全程都有內容，payload 不再獨自站在空白上。

修正後 WAV 與 MP3 320k 仍精準還原 delay=1129。

## 音樂會變嗎?（`check_audible_change.py`，已實測）

分兩層，結論不同。

### 加寬那層：完全沒變

| 指標 | 結果 |
|---|---|
| 單聲道總和 `L+R` 差異 | **−227.9 dB**（浮點數的零） |
| 各頻段振幅差異（20Hz–20kHz，8 段） | 全部 **0.00 dB** |

驗證了全通濾波器的理論保證：只改相位、不改振幅。音色與 EQ 平衡完全沒動。

### 破壞層：數字上變很多，但聽不出來

M/S + delay 是套用在**整個檔案**上，包含歌曲段：

| 指標 | 原始 | 題目檔播放時 |
|---|---|---|
| 左聲道 vs 原始 | — | corr +0.9999 |
| 右聲道 vs 原始 | — | corr −0.0352 |
| L/R 相關 | +0.9998 | −0.0352 |
| 左右音量差 | ~0 dB | 10.6 dB |

**但實聽確認：聽不出來。** 原因是這首歌接近單聲道，所以 Mid ≈ 完整的歌
（左聲道幾乎原封不動），而 Side 只有 −22 dB 很容易忽略；任何往單聲道混的
播放方式又會把 `L+R` 加回接近原曲。

因此**維持現狀**：破壞套用於整個檔案，不需要只針對 payload 段。
（若日後換成立體聲較寬的來源，這個結論要重新驗證 —— 那時 Side 不再是小訊號。）

## 難度評估（對 AI agent）

主要門檻在**視角**，不在計算：

- agent 的標準流程是「畫波形 → 畫頻譜 → 看 metadata → binwalk」，
  這四步在本題全部無效。
- 「把立體聲當 X-Y 散點圖畫」不在預設清單裡，這是最大的一道關。
- 但一旦想到了，後面的 cross-correlation / 參數搜尋 agent 反而比人類快。

預期效果是把 agent 從 5 分鐘拉到 40–90 分鐘，而不是歸零。

## 調整參數

改 `generate.py` 開頭的 config 區塊：

- `FLAG_LINES` — 換 flag（支援任何 DejaVu Sans 有的字元）
- `DELAY` — 換延遲量（建議 500–3000，避開整除 `FRAME_SAMPLES` 的值）
- `FRAME_SAMPLES` — 調高 = 字更細緻但 refresh 更慢
- `CARRIER_SECONDS` / `CARRIER_LEVEL` — 前後的環境音襯底

改完重跑：

```bash
python3 generate.py && python3 solve.py challenge.wav
```

## 出題提醒

- **提交要寬容**：希臘字母選手很可能打不出來或搞混（δ/ό、κ/k、ς/σ）。
  建議後端做正規化，或在題目敘述提供希臘字母鍵盤/對照表連結。
  `ς`（字尾 sigma）和 `σ` 特別容易錯。
- `reference_clean.wav` **不要發布**。
- payload 段是刺耳嗡鳴，這是正常的（也是提示）。歌曲版本的其餘部分
  聽起來與原曲無異 —— 見「音樂會變嗎?」一節。
